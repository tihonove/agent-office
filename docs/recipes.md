# Готовые схемы

Три типовых пути заявки. Каждая схема — готовый каталог `recipes/<схема>/`: манифест, промпты ролей и заглушки.
Копируется в корень проекта целиком и сразу проходит прогон `--fake` — это закреплено тестами офиса.

```
cp -r <docs>/recipes/<схема>/. <проект>/
agent-office <проект> --fake
```

| Схема | Роли | Человек | Когда брать |
|---|---|---|---|
| [`конвейер`](recipes/конвейер/office.yaml) | аналитик, реализатор | принимает результат | старт по умолчанию: «офис с аналитиком и реализатором» |
| [`согласование`](recipes/согласование/office.yaml) | аналитик, реализатор | согласует постановку, принимает результат | реализация дорогая, и человек хочет решать, что делать |
| [`декомпозиция`](recipes/декомпозиция/office.yaml) | штурман, аналитик, реализатор | принимает результат каждой части | заявки бывают большими и делятся на независимые части |

Во всех схемах молчание человека (`default` запроса) — `отложить`: заявка откладывается, ничего не запускается.
Вернуть отложенную — вызвать нужную роль руками на карточке узла.

## Конвейер

```
новая ─аналитик→ к реализации ─реализатор→ приёмка ─«принять»→ готово
                                                   ─«вернуть»→ к реализации
                                                   ─«отложить» / молчание→ отложена
аналитик: «отказ» → отклонена
```

- **аналитик** (`when: новая`, `needs: [описание]`) читает заявку и код, публикует `постановка` для `[реализатор]`,
  заявляет `готово` с полем `критерий` — или `отказ`.
- **реализатор** (`when: к реализации`, `needs: [критерий]`, `sees: постановка, отчёт`) работает в worktree
  `.worktrees/<узел>`, публикует `отчёт` для всех, заявляет `готово`.
- **запрос `приёмка`** на состоянии `приёмка`; переходы — на каждый вариант. Для «вернуть» человек сначала пишет
  поле `замечания`: реализатор видит его в `узел.md` и свой прошлый `отчёт` в проекции.

Файлы: [office.yaml](recipes/конвейер/office.yaml), [аналитик](recipes/конвейер/office/roles/аналитик.md),
[реализатор](recipes/конвейер/office/roles/реализатор.md), заглушки `recipes/конвейер/fake/`.

## Согласование человеком через запрос

Как конвейер, но между аналитиком и реализатором стоит человек. Гейтов в офисе нет: «гейт» собран из
состояния-ожидания `согласование`, объявленного запроса на нём и перехода на каждый вариант ответа.

```
новая ─аналитик→ согласование ─«делаем»→ к реализации ─реализатор→ приёмка ─«принять»→ готово
                              ─«переделать»→ новая          (аналитик пишет новую редакцию)
                              ─«не делаем»→ отклонена
                              ─«отложить» / молчание→ отложена
```

Ключевой кусок манифеста:

```yaml
transitions:
  - { kind: заявка, from: согласование, to: к реализации, when: { answer: { request: постановка, is: делаем } } }
  - { kind: заявка, from: согласование, to: новая,        when: { answer: { request: постановка, is: переделать } } }
  - { kind: заявка, from: согласование, to: отклонена,    when: { answer: { request: постановка, is: не делаем } } }
  - { kind: заявка, from: согласование, to: отложена,     when: { answer: { request: постановка, is: отложить } } }

requests:
  - id: постановка
    when: { kind: заявка, state: согласование }
    question: Аналитик подготовил постановку. Что делать будем?
    options: [делаем, переделать, не делаем, отложить]
    default: отложить
    deadline: 3d
```

«Переделать» возвращает узел в `новая` — новая эпоха состояния, и аналитик поднимается снова. Его промпт
умеет узнать доработку: поле `замечания` или прошлая постановка в проекции (`sees: '*'` от себя).

Файлы: [office.yaml](recipes/согласование/office.yaml), [аналитик](recipes/согласование/office/roles/аналитик.md),
[реализатор](recipes/согласование/office/roles/реализатор.md), заглушки `recipes/согласование/fake/`.

## Декомпозиция через порождение

На входе штурман решает курс: вести целиком, разбить или отказать. Разбивает он артефактом `курс`
со списком `nodes` в шапке; дочерние узлы создаёт офис по объявлению `spawns`.

```
новая ─штурман: «в работу»→ к анализу ─аналитик→ к реализации ─реализатор→ приёмка ─«принять»→ готово
      ─штурман: «разбито» + курс→ разбита
      ─штурман: «отказ»→ отклонена

дети курса рождаются в «к анализу» — мимо штурмана — и идут тем же путём, не больше двух открытых сразу;
разбита → готово, когда все дети в готово или отклонена
```

Ключевой кусок манифеста:

```yaml
spawns:
  - { artifact: курс, kind: заявка, state: к анализу, requires: [описание], maxOpen: 2 }

transitions:
  - { kind: заявка, from: разбита, to: готово, when: { children: { all: [готово, отклонена] } } }
```

Три вещи, без которых порождение ломается:

- дети рождаются в состоянии, куда **не смотрит** штурман, иначе он разобьёт их снова;
- у аналитика `sees: { kind: '*', from: [self, ancestors] }` — так он видит курс родителя;
- у родителя есть переход по `children`, иначе учётный узел навсегда останется в `разбита`.

На заглушках штурман всегда разбивает (так написан `fake/штурман/`): прогон проверяет весь путь с детьми.
Проверить исход «в работу» — замени `fake/штурман/` на один `результат.md` с `outcome: в работу`.

Файлы: [office.yaml](recipes/декомпозиция/office.yaml), [штурман](recipes/декомпозиция/office/roles/штурман.md),
[аналитик](recipes/декомпозиция/office/roles/аналитик.md), [реализатор](recipes/декомпозиция/office/roles/реализатор.md),
заглушки `recipes/декомпозиция/fake/`.

## Что обычно добавляют

- **Ревьюер** между реализатором и приёмкой: состояние `к ревью`, роль с исходами `{ годно: приёмка, переделать: к реализации }`,
  `sees: [{ kind: отчёт }, { kind: постановка }]`.
- **Роль вливания** после приёмки: состояние `к вливанию`, промпт «влей ветку из отчёта в основную, прогони проверки»,
  исполнитель с правами на `git merge`.
- **Поле `область`** от аналитика и `areas` в манифесте — чтобы реализатор знал, где искать.
