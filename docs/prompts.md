# Как писать промпт роли

Промпт — markdown-файл, путь к которому указан в `roles.<роль>.prompt`. Живой исполнитель запускает

```
claude -p '<промпт роли> + <хвост офиса>' --add-dir <назначение> --model <model> <args…>
```

в **корне проекта**. Хвост офиса дописывается сам и говорит агенту, где его назначение:
«прочитай `<назначение>/повод.md`, затем `проекция/`, исходящие клади в `out/`». Правила разговора с офисом
(таблица файлов `out/`) агент найдёт в `повод.md` — повторять их в промпте не нужно. Промпт говорит о деле:
что прочитать, что решить, что опубликовать и какой исход заявить.

## Что агент видит

Каталог назначения `.office/назначения/<роль>/<узел>/`:

```
повод.md          почему подняли именно сейчас + памятка, как говорить с офисом
проекция/         только чтение (права на запись сняты)
  узел.md         id, род, состояние, все поля узла; предки и дети
  области.md      карта areas, если объявлена
  артефакты/      a-<n>-<вид>.md — отобранные артефакты: шапка YAML (id, узел, вид, автор, аудитория, meta) + текст
  артефакты/не-вложено.md   адресованные роли, но не отобранные правилом sees — можно дотянуть
out/              сюда агент пишет; офис заберёт файлы, когда агент завершится
транскрипт.jsonl  вывод claude (для человека)
```

Поводы бывают такие: «Первый заход на этот узел», «Узел снова там, где нужна твоя роль. Прошлый заход закончился
исходом …», «Прошлое воплощение завершилось без результата» (с причинами, если офис что-то отклонил),
«На твой вопрос … человек ответил: …», «Роль вызвана человеком руками».

Что попадёт в `артефакты/`, решают две вещи сразу:

- **аудитория** артефакта (её пишет автор) — потолок: артефакт для `[реализатор]` аналитик не увидит никогда;
- **правило `sees`** роли (его пишет манифест) — что роли нужно: `{ kind: постановка }`, `{ kind: '*', from: [self, ancestors] }`.

Отсюда правило согласования: **вид и аудитория, которые промпт велит публиковать, должны совпадать с `sees`
роли-читателя.** Аналитик публикует `постановка` для `[реализатор]`, у реализатора `sees: [{ kind: постановка }]`.
Сомневаешься в аудитории — пиши `['*']`.

Поля узла видны всем ролям в `узел.md`, без всяких `sees`. Поэтому короткие вещи, нужные следующей роли
(критерий, область, замечания человека), удобнее передавать полями, а длинные — артефактами.

## Как агент говорит с офисом: `out/`

Файл = шапка YAML между строками `---` + текст. Имя файла определяет, что это:

| Файл | Шапка | Текст | Что делает офис |
|---|---|---|---|
| `артефакт-<имя>.md` | `kind`, `audience`; прочие ключи — шапка артефакта | тело | публикует артефакт на узле |
| `результат.md` | `outcome`; необязательно `fields: { поле: строка }` | пояснение | дописывает поля, закрывает заход, двигает узел по `arrows.outcomes` |
| `вопрос.md` | `options` (≥ 2), `default` (из options), необязательно `deadline` | вопрос | открывает запрос человеку; агент ждёт ответа в офисе |
| `флаг-<имя>.md` | — | что не так | показывает флаг человеку, ничего не двигает |
| `дотянуть.md` | `artifacts: [a-3, …]` | — | поднимет агента снова, добавив эти артефакты в проекцию |

Примеры:

```
---
kind: постановка
audience: [реализатор]
---
Что сделать, чего не делать, как проверить.
```

```
---
outcome: готово
fields:
  критерий: кнопка «Выход» есть на каждой странице и разлогинивает
  область: интерфейс
---
Постановка опубликована.
```

```
---
options: [oauth, пароль]
default: пароль
deadline: 4h
---
Вход делать через OAuth или по паролю?
```

Правила, которые стоит отразить в промпте:

- **Каждый заход кончается ровно одним из трёх:** `результат.md`, `вопрос.md` или `дотянуть.md`. Без них заход
  потерян: офис вернёт узел и поднимет роль снова, после трёх потерь подряд — только флаг.
- **Исходы — ровно те, что в `arrows.outcomes` роли.** Перечисли их в промпте дословно, с тем, что каждый значит.
  Другой исход офис отклонит.
- **Поля — строки.** `fields: { критерий: … }`; списки и числа офис не примет. Поля, которые нужны следующей роли
  в `needs`, промпт должен велеть записать — иначе следующая роль не поднимется.
- **Порядок приёма:** артефакты и флаги → результат → дотянуть → вопрос. Сначала публикуй, потом заявляй исход.
  Вопрос вместе с результатом бессмыслен: после результата заход закрыт, вопрос офис отклонит.
- **Спросил — завершайся.** Агент без интерфейса ответа не дождётся. Офис поднимет тот же ключ, когда человек ответит
  или выйдет дедлайн (тогда — с вариантом `default`); ответ будет в `повод.md`. Если с прошлого захода прошло меньше
  `resumeWithin`, агент продолжит ту же сессию и помнит разговор.
- **Порождение:** артефакт вида из `spawns` обязан иметь в шапке непустой список `nodes`, каждый элемент —
  набор строковых полей, включая `requires`. Иначе офис отклонит артефакт, а исход (например, `разбито`) примет —
  и родитель застрянет без детей. Дай в промпте пример шапки целиком.
- **Отклонённое** офис кладёт в `out/отклонено/`, принятое — в `out/принято/`. Причины отказа следующее воплощение
  найдёт в `повод.md`.

## Офис не знает git

Офис запускает агента в корне проекта и больше ничего о коде не знает: ни веток, ни worktree, ни слияний.
Где и как работать с кодом, говорит **промпт**. Для ролей, которые меняют код, обычная схема:

- работать в отдельном git worktree, ветка по id узла: `git worktree add .worktrees/<id> -b <id>`
  (id — в заголовке `проекция/узел.md`); ветка уже есть — продолжать в ней;
- основное дерево не трогать: в нём одновременно работают агенты других узлов;
- коммитить в свою ветку, не пушить и не вливать; путь к worktree и ветку — в артефакт-отчёт;
- вливает человек (или отдельная роль с таким промптом).

Роли, которые код только читают (аналитик), так и пишут: «код проекта не меняй».

## Права агента

`claude -p` работает без интерфейса: разрешения спросить не у кого, и всё, что не разрешено заранее, просто не выполнится.
Права — это `args` исполнителя в манифесте:

| Аргумент | Что даёт |
|---|---|
| `--permission-mode acceptEdits` | читать и править файлы в корне проекта и в назначении — без этого агент не сможет даже записать `out/` |
| `--allowedTools 'Bash(git *)' 'Bash(npm *)'` | запуск этих команд. Шаблон на команду; всё прочее в Bash запрещено |
| `--model` | не нужен: для модели есть ключ `model` |

```yaml
executors:
  читатель:    { type: claude, model: sonnet, args: [--permission-mode, acceptEdits, --allowedTools, 'Bash(git log *)', 'Bash(git show *)'] }
  разработчик: { type: claude, model: sonnet, args: [--permission-mode, acceptEdits, --allowedTools, 'Bash(git *)', 'Bash(npm *)', 'Bash(npx *)'] }
```

Проверь, что команды из промпта (тесты, сборка, линтер) покрыты `--allowedTools` исполнителя этой роли.
Несовпадение не даёт ошибки на старте: агент тихо не сможет выполнить команду и, скорее всего, сдаст непроверенное
или потеряется. Разным ролям — разные исполнители с разными правами.

## Скелет промпта

```
Ты — <роль>. <Одна фраза: за что отвечаешь и чего не делаешь.>

Прочитай `проекция/узел.md` (<какие поля важны>) и `проекция/артефакты/` (<какие виды там будут>).
<Если это доработка — как её узнать (поле «замечания», прошлый артефакт) и что делать иначе.>

<Где работать: «код не меняй» или правила worktree.>

<Что опубликовать: вид, аудитория, что в тексте, что в шапке.>

Заяви результат:
- `<исход 1>` — <когда>; допиши поля `<поле>` (<что в нём>).
- `<исход 2>` — <когда>.

Не хватает решения человека — задай вопрос (варианты и вариант по умолчанию) и заверши работу.
```

Готовые промпты — в `recipes/*/office/roles/`.
